# JK03A – журнал разметки дефа

RE-журнал рабочего дефа `JK03A.xml` под дамп `rom-images/v36-vq25hr-jk03a/as7058.bin`
(Nissan Skyline V36 250GT, VQ25HR, 23710-JK03A, SH7058 / 1 MiB, JDM).
sha256 `f78929547c08dc5ecde256fb3a6f6f3ef6daa9010e1531b3eac99fd9509225b4`.

## Статус

- Опознавание: рабочее. Дамп самоидентифицируется строкой `JK03A` по адресу `0x8205`
  (= `internalidaddress` дефа) и калибровкой `1JK03A00000`. RomRaider опознает ROM как
  JK03A из romid-скелета.
- JK03A импортирован в Ghidra-проект `vq-hr` (`SuperH:BE:32:SH-2A`, base 0x0, 1 MiB),
  автоанализ выполнен; трейс аксессоров через `FindTableRefs`/`DecompileFuncs`/`DumpListing`
  работает.
- Размечено [CONFIRMED]: ignition-семейство - три карты 16x16 uint8
  `0xB61A/0xB71A/0xB81A` через интерполятор `0x26320`. Оси: RPM `0x11B6B`
  (строки) x нагрузка `0x11B8B` (столбцы). Плюс ось `0x11ECE` (RPM, `x*50`)
  аксессора `0x4bbee`.
- Размечено [CONFIRMED]: интерполяторный кластер - общий kernel `0x26944` плюс
  обёртки по размерности (`0x26320`=16x16, `0x26084`=4x4, `0x264a0`=1D-16).
  Найдено 4x4-семейство `0xA49A`/`0xAB6A` (аксессоры `0x52f00`/`0x54ee0`, оси
  `0x11D00`/`0x11B67`, interp `0x26084`) и 1D-кривая `0x129D2` (`0xb997c`, ось
  `0x11B7B`, interp `0x264a0`) - геометрия подтверждена, семантика TBD.
- Инвентаризация interp-семейства (`MapInventory.java` по kernel `0x26944`): 11 обёрток-
  интерполяторов, 124 места вызова, 94 различимых таблицы. 16x16-2D обёртки
  (кроме ignition) - `0x261b8` и `0x261f0`. Зоны таблиц: `0x9xxx`/`0xAxxx`/`0xBxxx`
  и крупный кластер `0x12xxx` (обёртка `0x26474`, ~45 карт по 8 широких). Перепись
  замкнута внутри своего семейства и не покрывает прямой lookup `0x26370`.
- Прогресс по картам - ledger `JK03A.maps.csv`: строка на карту (обёртка, размерность,
  оси, аксессоры, `status`, имя). Сырьё - `reference/JK03A.map_inventory.csv`
  (пересъём - `MapInventory.java`), пересборка - `tools/maps/build_tracker.py`:
  механические колонки берутся из переписи, разметка `status`/`name`/`note`
  переносится из ledger'а. Счётчики готовности печатает сам скрипт - в журнале
  не дублируются. Состав ledger'а: 94 kernel-таблицы + 18 сайтов с неснятым `r4`
  + rev-лимитер (читается не через kernel). Охват - только interp-семейство; карты
  прямого lookup'а `0x26370` в ledger'е не представлены.
- Размечено [CONFIRMED]: AFR/lambda - `0xB33A` (Target AFR power, плато 14.7 +
  обогащение 11.2) и `0xA29A` (плоский lambda 14.0..14.8), обе 16x16 `1881.6/x`,
  записаны в деф.
- Размечено [CONFIRMED]: осевая семантика всех карт через kernel `0x26944` - ось
  X-обёртки = обороты (общий вход `byte[0xFFFF11AE]`), ось Y = нагрузка; finisher
  кладёт RPM в строки, нагрузку в столбцы. В RomRaider X Axis=нагрузка, Y Axis=RPM
  - исправлено на всех 5 картах. Множитель RPM `x*50` [CONFIRMED]
  (скорость в единицах rpm/50, см. "Множитель оси RPM = 50").
- Размечено [CONFIRMED] (геометрия/оси): транзиентная коррекция accel/decel -
  8x8 `0xAB0A`/`0xB23A` через аксессор `0xbefb0` (ветвление по `dQ/dt`), записаны
  в деф; условный выбор карт `0xABFA`/`0xABBA` через `0xa52e4` - в notes.
  [CANDIDATE]: идентичность по A2L, единицы значений.
- Размечено [CONFIRMED]: rev-лимитер fuel-cut - `word[0xFFFF266E]` (rpm/12.5) vs пороги
  `0x8FDC=7625`/`0x8FDE=6600 rpm` (выбор флагом `0xFFFF246D bit7`), выход `0xFFFF246A
  bit7`, аксессор `FUN_00047a56`; записан в деф. [CANDIDATE] по ProECU-гайду: пара -
  `Rev Limit - Fuel Cut Maximum` (верхнее = отсечка, нижнее = восстановление), селектор -
  состояние "отсечка активна"; отдельные 2D-карты рабочего лимита не локализованы.
- Второе семейство доступа к картам [CONFIRMED]: прямой lookup `0x26370` - 8-точечный
  интерполятор с неявной линейной осью шага 32 (реальный поиск в `0x26A80`), указателя оси
  нет. 61 pool-слот по всему ROM против 11 у `0x26944`, слоя обёрток нет, слот != вызов.
  Kernel-перепись его структурно не видит; ledger покрывает только interp-семейство.
  Зона таблиц - `0x12xxx`. См. "Прямой lookup `0x26370`".
- Размечено [CONFIRMED]: overrun fuel cut читает пороги через `0x26370` - `FUN_0005185c`
  делает 6 lookup'ов (`0x1220E`/`0x121FE`/`0x121AE` по `byte[0xFFFF106F]`,
  `0x121D6`/`0x121C6` по `byte[0xFFFF11B3]`, `0x121DE` по `word[0xFFFF1024]>>7`).
  [CANDIDATE] `mTNJC`/`mTNR`: пара `0x121FE` = `2050..1250 rpm` (отсечка) и `0x12206` =
  `1350..900 rpm` (восстановление) при `x*25`, гистерезис по температуре ОЖ; совпадает с
  `Over Run Fuel Cut #2`/`Restore #2` ProECU. Исполнение отсечки - поцилиндровое
  `FUN_00051a98`. См. одноимённую секцию.
- Размечено [CONFIRMED]: K2Y decel-угол - расчёт угла `0x82c8a` не адресует ни одной базы
  decel/cut-флагов => decel-gated ветки advance в нём нет; `mTKADVA` не выражен ни одной
  картой interp-семейства. Тот же расчёт использует `0x26370` (слот `0x838bc`) - его
  таблицы не каталогизированы, decel-advance через это семейство не исключён.
- Не размечено: MAF, injector latency, speed-лимитер, кластер `0x12xxx`. Полнота требует
  двух цензов - по kernel `0x26944` и по примитиву `0x26370`.

## Метод

Готового дефа под JK03A нет. Reference-деф `Pytrex .../G35/JK03A.xml` – пустой
опознаватель (romid + checksum, 0 таблиц). Донор структуры **EV18A** (350Z HR,
SH7058/1MB non-VVEL, тот же `internalidaddress=0x8205`, 190 таблиц) даёт имена/оси/
scaling через наследование `base="A2L"`, но его `storageaddress` на наш дамп не
ложатся: проверено – `Load Base Fuel @0x16A00` = сплошной `0x8000` (padding),
`Target Idle RPM @0x1472D` = мусор. Layout калибровки JDM 2.5L отличается от USDM 3.5L.
Даже EV15A и EV18A (оба 350Z HR) имеют разные адреса тех же карт. => адреса ищутся в
самом дампе.

Геометрия таблиц (размеры/тип/scaling/оси) идентична семейству HR и берётся из каталога
`A2L.xml`; отличаются только адреса. Ключевые карты (из A2L):
- Ignition timing maps 16x16 uint8, scaling `Degrees Adjustment (x-64)`, оси
  X=Cylinder Filling, Y=Engine Speed (обе динамические, uint8, 16 точек).
  В EV18A три подряд шаг `0x100`: Cold `0x9976` / HiOct `0x9A76` / HiDet `0x9B76`,
  общие оси X `0x13E9B` / Y `0x13EAB`.
- Target AFR Map 16x16 uint8, scaling `1881.6/x`, те же оси.
- Rev Limit (Fuel Cut) uint16 2x2, scaling `RPM (x*12.5)`.

Инструменты разметки (scratchpad, воспроизводимо):
- `a2l_geom.py` – геометрия таблиц из A2L.
- `find_maps.py` – скан пар монотонных uint8-осей и троек 16x16-блоков.
- `ptrscan.py` – скан 32-бит BE указателей на калибровочные зоны (базы таблиц).
- `viz.py` – печать 16x16-блоков и осей для визуальной идентификации.

## Подтверждено [CONFIRMED]

### Ignition-семейство – `0xB61A / 0xB71A / 0xB81A` (аксессор FUN_00082c8a)

`FindTableRefs 9000..c000` + агрегация по функции (`agg_tref.py`): единственная
функция с тройкой баз шаг `0x100` – `FUN_00082c8a` (@0x82c8a) грузит
`0xB81A/0xB61A/0xB71A`. asm @`0x832a0` (`DumpListing`):

```
mov.l ...,r4 = 0000b81a   ; TABLE
mov.l ...,r5 = 00011b6b   ; AXIS X
mov.l ...,r6 = 00011b8b   ; AXIS Y
mov.l ...,r2 = 00026320   ; INTERP
jsr  @r2                  ; interp(table, axisX, axisY, cur_x, cur_y)
mov.b r2,@(ffff314a)      ; результат в RAM
```

- Карты: три 16x16 uint8, первая строка общая `[41,41,41,43,43,43,43,44,45,46,
  47,48,48,48,48,48]`, расходятся ниже. Выбор по флагу `gbr+0x93` bit0: `0xB81A`
  всегда, `{0xB61A|0xB71A}` по флагу => семейство Cold/HiOct/HiDet (A2L).
- Оси (по 16 монотонных точек; привязка строки/столбцы - в разделе "Оси карт"):
  - `0x11B6B` (обороты, строки): `[12,16,20,24,32,40,50,60,70,80,90,100,110,120,
    130,150]`, `x*50` => 600..7500.
  - `0x11B8B` (нагрузка, столбцы): `[8,16,20,24,28,32,36,40,44,48,56,64,80,96,112,
    136]`.
- Интерполятор `FUN_00026320` (48 B) – обёртка над примитивами `0x26350/0x26354`.
  У `0x26320` единственный вызывающий (0x82c8a) => локальная обёртка; реально
  общий interp = примитивы, достижимы через `PTR_FUN`-слоты (=> граф-каталог).
- Scaling карт: A2L "Degrees Adjustment (x-64)"; сырьё `0xB61A` = `[-23..64]` при
  x-64 (adjustment, не абсолютный advance). Оси: обороты `0x11B6B` (строки) x
  нагрузка `0x11B8B` (столбцы) - см. "Оси карт". [CANDIDATE]: точный множитель
  scaling карты.

### Интерполяторный кластер - общий kernel `0x26944`

Интерполируемая карта читается через тонкую обёртку-интерполятор, а обёртки делят один
first-stage kernel. Значения указателей (BE u32 из дампа):

```
PTR@0x26354 = 0x26944   PTR@0x26350 = 0x268a4   (обёртка 0x26320, 16x16)
PTR@0x260b8 = 0x26944   PTR@0x260b4 = 0x26770   (обёртка 0x26084, 4x4)
PTR@0x264c8 = 0x26944   PTR@0x264c4 = 0x26740   (обёртка 0x264a0, 1D-16)
```

- `0x26944` - общий kernel (первый вызов в каждой обёртке); finisher-указатель
  (`0x268a4`/`0x26770`/`0x26740`) специфичен под размерность. Декомпиляция обёрток:
  константа = размер оси (`0x10`=16 => 16x16; `4` => 4x4; `0xf` => 16-точечная 1D).
- Следствие: дерево вызовов `0x26944` = полный каталог интерполируемых карт. Каждый
  вызывающий грузит `r4`=table, `r5`/`r6`=оси перед `jsr`; обёртка задаёт размерность.
  Карты с неявной осью сюда не входят - см. "Прямой lookup `0x26370`".

### Прямой lookup `0x26370` - второе семейство доступа к картам

Второй примитив чтения таблиц, независимый от interp-kernel. `FUN_00026370` (18 B):

```
if ((index & 0xff) < 224) tail-jump 0x26A80(table, index)   // реальный поиск
return byte[table + 7];                                     // index >= 224 -> последняя точка
```

`0x26A80` начинается с пяти пар `SHLR R5` / `ROTCR R3` = 64-битный сдвиг пары `(r5:r3)`
вправо на 5. Значит `index = raw >> 5` (0..6), младшие 5 бит остаются дробной частью для
интерполяции; граница `224 = 7*32` в `0x26370` даёт точку 7.

=> `0x26370` - 8-точечный интерполированный lookup с неявной линейной осью шага 32 по
сырому байту датчика (0..255). Указателя оси нет: ось зашита в арифметику, отдельной
таблицы breakpoint'ов не существует. Зона таблиц семейства - `0x12xxx`.

Масштаб: 61 pool-слот с адресом `0x26370` по всему ROM (у `0x26944` - 11, все внутри
кластера обёрток). Слоя обёрток нет, аксессор зовёт примитив напрямую, и слот != вызов:
`FUN_0005185c` держит один слот `0x5197c` и делает им 6 lookup'ов по разным таблицам.

Следствие для переписи: `MapInventory.java` построен на тройках `(таблица, ось_X, ось_Y)`
и структурно не видит семейство без оси. Ledger `JK03A.maps.csv` описывает только
interp-семейство; второе семейство требует отдельного ценза по своей модели (аксессор
зовёт примитив напрямую; снимать `r4`=таблица, `r5`=вход).

### Оси карт: RPM=строки (Y), нагрузка=столбцы (X) - доказано трейсом

kernel `0x26944` - одномерный axis-search: читает `byte[axis + i]` от `i=15` вниз,
ищет первый break-point `<=` текущего значения, затем вторая стадия (`PTR@0x26980`)
берёт дробную часть. Обёртка зовёт kernel дважды: сначала для `r5`=ось X-обёртки с
текущим значением в `r7`, затем для `r6`=ось Y-обёртки с текущим из стека; оба
индекса идут в finisher.

finisher (`0x268a4` ignition, `0x26770` AFR/lambda) адресует ячейку:
`cell = table + idxY_wrap + idxX_wrap * 0x10`, где индекс по оси X-обёртки
домножается на 16 => **ось X-обёртки = строки (медленный индекс), ось Y-обёртки =
столбцы**.

Текущее значение оси X-обёртки во ВСЕХ трёх семействах (ignition, AFR-power,
lambda) - одна RAM-переменная `byte[0xFFFF11AE]` (`0xFFFF119C`+`0x12`), в
независимых аксессорах `0x82c8a` и `0xbfdc0`. Значения оси X-обёртки везде -
RPM-диапазон (600..7500) => `0xFFFF11AE` = текущие обороты. Ось Y-обёртки питается
другими переменными нагрузки: ignition - старший байт `word[0xFFFF1024]`, lambda -
`word[0xFFFF11F4]`.

Итог для RomRaider (перевод "оси обёртки" -> "оси таблицы"): **X Axis (столбцы) =
нагрузка, Y Axis (строки) = обороты.** Проверка физикой на 5/5 картах
(`transpose_all.py`): timing зажигания растёт с RPM (строки `+`) и падает с
нагрузкой (столбцы `-`); AFR-raw богатеет к высокой нагрузке (столбцы `+`), сильнее
всего на `0xB61A/0xB71A`. Осевая СЕМАНТИКА доказана; МАСШТАБ RPM `x*50` [CONFIRMED]
(скорость хранится в единицах rpm/50, см. "Множитель оси RPM = 50").

### Множитель оси RPM = 50 (скорость хранится в единицах rpm/50)

Осевой вход `byte[0xFFFF11AE]` пишется через указатель: структуру `0xFFFF119C`
заполняет по указателю-аргументу функция-обработчик, поэтому reference-анализ не
даёт ни одной резолвнутой записи (`W`) во всём диапазоне `0xFFFF119C..0xFFFF11B7`,
тогда как соседние абсолютно-адресуемые сенсоры (`0xFFFF11D4..0xFFFF11FC`,
`0xFFFF1198`) пишутся штатно (`ExportXrefs`: 56224 периферийных ссылки, 0 записей
в структуру). Явного деления `/50` у writer'а нет: скорость двигателя хранится
нативно в единицах rpm/50 (1 байт = 0..12750 rpm) - это и есть причина масштаба.

Множитель 50 подтверждён совпадением трёх независимых RPM-осей: только `m=50`
даёт и округлённую лесенку оборотов, и верную отсечку ~7500 у VQ25HR:
- ign `0x11B6B`: `600,800,1000,1200,1600,2000,2500,...,7500`;
- afr `0x12F2E`: `800,900,1000,1200,...,6400`;
- lam `0x11CF0`: `400,800,1200,...,7400`.
Плюс `0xFFFF11AE` - доказанный общий индекс оборотов (осевой вход ignition + AFR +
~40 потребителей). => `x*50` [CONFIRMED] как определение единицы, не оценка.

### Транзиентная коррекция (accel/decel) - `0xAB0A`/`0xB23A`, FUN_000befb0

Аксессор `0xbefb0` (8-wide обёртка `0x26140`) - транзиентная топливная коррекция:
две 8x8 uint8 карты через интерполятор, направление разгон/сброс выбирается знаком
производной расхода `dQ/dt` (ветвление вокруг нейтрали `0x32000000` = 50.0 в Q24).
Обе карты индексируются (RPM, нагрузка), значения используются в обеих ветвях:
- `0xAB0A` (магнитуда) - зависит только от RPM (плоская по нагрузке): `4..37`;
- `0xB23A` (вес) - плоская `27`.
Оси [CONFIRMED] кодом (DumpListing `0xbefb0`): curX = `byte[0xFFFF11AE]` (RPM) ->
ось X-обёртки (строки), curY = старший байт `word[0xFFFF1024]` (нагрузка, тот же
вход, что у ignition) -> ось Y (столбцы). Адреса: `0xAB0A` RPM `0x120AE` / load
`0x120B6`; `0xB23A` RPM `0x12858` / load `0x12860` (RPM-оси `[16,32,..,128]`*50 =
800..6400, load `[8,18,..,78]`). В деф записаны (X Axis=нагрузка, Y Axis=RPM x*50).
[CANDIDATE]: идентичность по A2L (mMITANDD/mMITANDA - Decel/Accel Fuel Compensation)
и физические единицы значений.

Условный аналог - `0xa52e4`: выбирает одну из двух 8x8-карт `0xABFA`/`0xABBA` (общая
ось RPM `0x12BE2` [800..3600], load `0x12BEA`) по условию `byte[0xFFFF3427] >
byte[0x8796]` (ROM-порог `0x5F`=95). Селектор-сенсор не опознан, семантика [CANDIDATE].

### Overrun fuel cut (decel) - таблицы порогов через прямой lookup `0x26370`

Отсечка сброса газа читает калибровочные таблицы через второй примитив доступа -
`0x26370` (см. "Прямой lookup `0x26370`"), а не через interp-kernel `0x26944`. Оси как
объекта у этого семейства нет, поэтому в kernel-переписи его таблицы отсутствуют.

`FUN_0005185c` (decel-detect, `0x5185c`, 388 B) держит указатель на примитив в слоте
`0x5197c` и делает им шесть lookup'ов [CONFIRMED кодом]:

| таблица | вход | слот |
|---|---|---|
| `0x1220E` | `byte[0xFFFF106F]` (= `0xFFFF1068+7`) | `0x519a4` |
| `0x121FE` | `byte[0xFFFF106F]` | `0x519a8` |
| `0x121AE` | `byte[0xFFFF106F]` | `0x51984` |
| `0x121D6` | `byte[0xFFFF11B3]` (= `0xFFFF119C+0x17`) | `0x519ac` |
| `0x121C6` | `byte[0xFFFF11B3]` | `0x519b0` |
| `0x121DE` | `word[0xFFFF1024] >> 7` | `0x519ac`+8 |

Кандидат на A2L `mTNJC`/`mTNR` (JECS cut/restore speed, uint8, `x*25`, ось = температура
ОЖ) - пара 8-точечных таблиц по `0x121FE`, вход `byte[0xFFFF106F]`:

- `0x121FE` = `[82,70,60,58,55,52,50,50]` -> при `x*25` = `2050..1250 rpm`;
- `0x12206` = `[54,53,50,46,44,39,36,36]` -> при `x*25` = `1350..900 rpm`.

Обе монотонно убывают по оси, вторая всюду ниже первой - форма гистерезиса
cut/restore: холодный двигатель отсекает и восстанавливает выше, горячий ниже.
Совпадает с описанием `Over Run Fuel Cut #2` / `Restore #2` в ProECU-гайде 370Z
(`refs/ecutek/`): порог оборотов для отсечки на сбросе газа, зависящий от температуры ОЖ.

[CONFIRMED]: примитив, шесть lookup-сайтов, адреса таблиц и входов.
[CANDIDATE]: идентичность `mTNJC`/`mTNR`, множитель `x*25` и парность `0x121FE`/`0x12206` -
`0x12206` эта функция не адресует, пара сведена по соседству и форме; нужен трейс
потребителя. Семантика `byte[0xFFFF106F]` (ожидается температура ОЖ) кодом не закреплена.

Поцилиндровое исполнение отсечки [CONFIRMED] - `FUN_00051a98`, цикл по 6 цилиндрам (V6).
Топливо присутствует только при выполнении AND-условия, ключевой калиброванный член -
`byte[0x87FD]<<3 (=25*8=200) <= (word[0xFFFF1024] - word[0xFFFF1028])` (дельта двух слов
нагрузки/расхода); остальные члены - поцилиндровые маски `byte[0xFFFF22E0]`,
`byte[0xFFFF128C+off]` и флаг `byte[0xFFFF245D] bit5`. Результат пишется битом на цилиндр
в cut-маску `byte[0xFFFF120E+0x12]`; при невыполнении топливо = 0.

Detect сброса газа [CONFIRMED] - знаковое `short[0xFFFF10B8] < -byte[0x86AE]` в том же
`FUN_0005185c`; `byte[0x86AE]=0` => порог нулевой, detect по любому отрицательному наклону
нагрузки. Выход - бит `0x10` в `byte[0xFFFF24D2]` (= база `0xFFFF24CE+4`).

Физический смысл слов `0xFFFF1024`/`0xFFFF1028` (расход vs цель либо две выборки MAF) не
опознан, поэтому количественный эффект правки `byte[0x87FD]` не предсказуем - в деф как
редактируемый скаляр не вынесен.

### Rev-лимитер (fuel cut по оборотам) - `0x8FDC`/`0x8FDE`, FUN_00047a56 [CONFIRMED]

Источник оборотов - `word[0xFFFF266E]` (единственный писатель `FUN_00020dfe` -
планировщик 124 задач; читается лимитером/топливом/зажиганием, обработанная скорость в
единицах rpm/12.5). Листинг `0x47b8a-0x47bb4`:
- `byte[0xFFFF246D] bit7 == 0` => порог `0x8FDC = 0x0262 = 7625 rpm`;
- `byte[0xFFFF246D] bit7 == 1` => порог `0x8FDE = 0x0210 = 6600 rpm`;
- `cmp/hs word[0xFFFF266E] >= порог` => установка бита отсечки `byte[0xFFFF246A] bit7`
  (иначе сброс).

[CONFIRMED] кодом: источник RPM, оба порога и их адреса, выход-флаг, логика сравнения.
[CANDIDATE]: множитель `x*12.5` (стандарт A2L `mNMAX2` + точное совпадение 7625 с redline
VQ25HR 7500; делением не доказан).

Идентичность пары [CANDIDATE] - `Rev Limit - Fuel Cut Maximum` по ProECU-гайду 370Z
(`refs/ecutek/`): верхнее значение = обороты отсечки, нижнее = обороты восстановления.
То есть `0x8FDC`/`0x8FDE` - пара cut/restore, а селектор `0xFFFF246D bit7` - состояние
"отсечка активна". Гипотезу закрывает трейс писателя `0xFFFF246D bit7`: совпадение с
выходом `0xFFFF246A bit7` доказывает гистерезис, иной писатель - режимный селектор.

Тот же гайд перечисляет отдельные 2D-карты `Rev Limit - Fuel Cut` и `Rev Limit - Fuel Cut
Restore`, задающие рабочий лимит ниже максимума (ось входа в гайде не определена). В дампе
не локализованы.

Записан в деф: `Rev Limit - Fuel Cut Maximum (0x8FDC)`, 2 ячейки uint16 `x*12.5`. Смежные
`0x8FD8=[6325,6050] rpm` - константы иных функций (`0x6edbc`/`0x7054a`), не rev-лимитера,
в карту не включены.

### K2Y decel-зажигание (`mTKADVA`) - decel-gated ветки в расчёте угла нет [CONFIRMED]

A2L `mTKADVA` (Deceleration Advance, 8 uint8, `Degrees`, статическая ось = MBT
`[0,8..56]`) не выражен ни одной картой interp-семейства. Три адресных факта:

- Расчёт угла `FUN_00082c8a` (`0x82c8a`, 6060 B, диапазон `0x82c8a..0x84436`) базовых карт
  `0xB61A/71A/81A` не адресует ни одной базы decel/cut-флагов: слотов с `0xFFFF24CE`,
  `0xFFFF246A`, `0xFFFF245C`, `0xFFFF2468` в его диапазоне нет (во всём ROM их 59/14/40/30
  соответственно). Значит decel-gated ветки advance внутри основного расчёта угла нет.
- Статическая ось MBT `[0,8,16,24,32,40,48,56]` физически есть в ROM по `0x12389`, но это
  голова общей линейной оси 0..128 шага 8 (`0x1238A`, 17 входов). Её читают `FUN_0008152a`
  (@0x81724) и `FUN_00081d74` (@0x81f56) через интерполятор `FUN_00082090(table, axis, x)`,
  где `x = byte[DAT_00082084+0x12]`, а table - НЕ градусная advance-карта, а fuel-обогащение
  (ASCII-метка "Jccastnonqu" в области `0x1236A`); выход умножается в топливную цепочку, не
  в угол. Ось общая, не K2Y-специфичная.
- Кривые `0x1261A` и `0x1263A`=`0x12CBE` в `FUN_00082c8a` интерполируются по RPM-оси
  `0x1264A` (`x*50`) и работают как оконные компараторы порогов: сравнение с текущим
  значением включает/выключает флаги коррекций (`pbVar5[0x3f]`, `pbVar5[0xbb]`). Это
  пороги-окна включения, а не таблицы прибавляемого угла.

Охват вывода: decel-gated advance отсутствует в основном расчёте угла, и `mTKADVA` не
выражен ни одной картой interp-семейства. Прямой lookup `0x26370` в этом расчёте
присутствует (слот `0x838bc`), его таблицы не каталогизированы - decel-advance через это
семейство в другой функции не исключён.

### 4x4-семейство `0xA49A` / `0xAB6A` (interp `0x26084`)

`FindTableRefs 11B60..11B90` -> аксессоры `0x52f00` (@0x52f58) и `0x54ee0` (@0x54fd0),
оба грузят `r4`=table, `r5`=`0x11D00`, `r6`=`0x11B67`, `r2`=`0x26084`, `jsr`. Обёртка
`0x26084` = 4x4. Оси по 4 точки: X `0x11D00` `[20,40,56,64]`, Y `0x11B67`
`[51,102,154,205]`. Табличный вход - сенсор `0xFFFF11AE` (тот же, что осевой вход
ignition => `0xFFFF11AE` общий осевой сенсор). Карты (16 B каждая):
- `0xA49A`: `[26,29,45,43 / 26,24,35,42 / 26,24,36,42 / 35,38,42,42]`.
- `0xAB6A` = `0xA49A + 0x6D0`: сосед-семейство, тот же скелет.
Семантика [CANDIDATE]: 4x4 uint8 малая карта/лимит, датчики не дотрейсены.

### 1D-кривая `0x129D2` (interp `0x264a0`, ось `0x11B7B`)

### AFR / lambda - `0xB33A` (power) и `0xA29A` (flat), обёртки 0x261b8 / 0x261f0

Inventory дал две 16x16-2D обёртки помимо ignition. Карты опознаны по шкале
`1881.6/x` (стехиометрия 14.7 => байт 128), семантика подтверждена формой:
- `0xB33A` [CONFIRMED] Target AFR (power): плато 14.7 на idle/cruise, обогащение
  до 11.2 в углу нагрузка/RPM. Аксессор `FUN_000BFDC0` (@0xBFE22), обёртка
  `0x261b8`. Оси gbr-relative (gbr=`0x12EA2`): X `0x12F2E`
  `[16,18,20,24,28,32,40,48,56,64,72,80,88,96,112,128]`, Y `0x12F0E`
  `[8,16,24,...,128]` (шаг 8).
- `0xA29A` [CONFIRMED] второй lambda-таргет, плоский 14.0..14.8 (замкнутый контур).
  Аксессоры `FUN_0002C648` (@0x2CC9C) и @0x3C292, обёртка `0x261f0`. Оси X
  `0x11CF0` `[8..148]` (RPM-подобная, x*50 => 400..7400), Y `0x11D4C` `[16..255]`

Оси [CONFIRMED] (см. "Оси карт"): обороты = ось X-обёртки (строки), нагрузка = ось
Y (столбцы); в дефе X Axis=нагрузка, Y Axis=RPM. [CANDIDATE]: множитель RPM `x*50`,
единицы нагрузки.
Замечание метода: обёртка `0x261b8` даёт РАЗНЫЕ оси на карту (gbr-relative
computed, не общий literal) - экстрактор sweep'а обязан снимать `gbr+offset`, не
только pc-literal (иначе `r5`/`r6` теряются, как в `MapInventory` backtrack).

### Аксессор-интерполятор FUN_0004bbee (`0x4bbee`)

`FindTableRefs 11ebe..11ece` -> единственный узел `0x4bbee`: `0x11EBE` грузится как
literal @`0x4bccc`, `0x11ECD` – direct @`0x4bcd0`. `DumpListing` резолвит literal-pool:
- ROM-таблицы: `0x11E9E`, `0x11EBE` (X), `0x11ECD` (Y RPM), `0x1243A`, `0x12462`.
- RAM: входы-сенсоры `0xFFFF119C`/`0xFFFF2466`/`0xFFFF128C`, выход `0xFFFF15ED`.

### Коррекция гипотезы pattern-scan

Заход "0x11EBE = общая пара осей RPM x Load для 16x16 ignition/fuel/afr карт" (по
структурной аналогии с EV18A + 3 pointer-хита) трейсом **не подтверждён**: оси
принадлежат локальной подсистеме `FUN_0004bbee`, не ignition-триплету. Из pattern-scan
устояла только RPM-семантика Y. Урок метода (см. Obsidian "RE-стек и реверс таблиц"):
pattern recognition даёт кандидатов, семантику решает трейс кода.

## Зоны-кандидаты [CANDIDATE] – требуют подтверждения кодом

- Ignition timing: РАЗМЕЧЕНО кодом в `0xB61A/0xB71A/0xB81A` (см. CONFIRMED), НЕ в
  `0x97xx`. Гипотеза pattern-scan про гладкие поверхности `~0x9700..0x9C00` и
  аналогию с EV18A `0x99xx` – мимо зоны: адрес дал трейс аксессора, не `viz.py`.
  Ещё один урок "pattern != семантика".
- Сильные pointer-якоря без атрибуции: `0x0975A` (13 ссылок), `0x11FB6` / `0x11EBE`
  (по 3). Кластеры указателей в `0x16000..0x163xx` – калибровочная зона (fuel/torque).
- Rev-лимитер: РАЗМЕЧЕН кодом (`0x8FDC`/`0x8FDE` через `FUN_00047a56`, см. секцию
  "Rev-лимитер"). Прежний data-scan (24 кандидата uint16 в `0x08FD8..0x191FE`) без кода
  неоднозначен - адрес дал трейс сравнения `word[0xFFFF266E] >= порог`, не скан.

## Следующий шаг

Инвентарь interp-семейства разложен в ledger `JK03A.maps.csv` - он же worklist sweep'а:
работа идёт по строкам со `status` = `unopened`/`unresolved`, результат разбора
карты пишется в её строку (`status`/`name`/`note`).

Полнота каталога требует **второго ценза - по примитиву `0x26370`**. Его модель другая:
слоя обёрток нет, аксессор зовёт примитив напрямую, ось неявная. Снимать нужно `r4`
(таблица) и `r5` (вход) на каждом сайте вызова, стартуя с 61 pool-слота. Пока этот ценз
не снят, о полноте разметки карт говорить нельзя, а negative-выводы вида "такой карты нет"
недопустимы: их область действия ограничена одним семейством.

Sweep каталога:
1. Снять оси на каждый сайт устойчиво: и pc-literal, и gbr-relative (`stc gbr,rN;
   add #off`). `MapInventory` backtrack берёт только literal - отсюда 18 сайтов
   без `r4` и часть пустых осей. gbr - константа (`0x12EA2`), резолвится Ghidra.
2. Классифицировать по размеру (из обёртки), шкале `A2L` и сигнатуре значений:
   MAF, injector latency, rev/speed limiter (uint16), крупный кластер `0x12xxx`
   (обёртка `0x26474`, ~45 карт по 8 широких). Доноры-чек-листы имён/геометрии (не
   адресов): EV18A и ProECU-гайд 370Z (`refs/ecutek/`, стоковые карты VQ37VHR; VVEL-
   специфика к non-VVEL VQ25HR неприменима).
3. Записать в `JK03A.xml`; проверять формой карты и downstream RAM-выходом.
Масштаб (94 карты interp-семейства плюс не снятый ценз `0x26370`) -> кандидат под
dynamic-workflow, как immo-реверс проекта (параллельная трассировка + adversarial поверх
headless-артефактов). Граф JK03A в Memgraph (`ExportGraph.java`) даёт caller-tree
`0x26944` напрямую.

Осевая семантика (обороты vs нагрузка, строки/столбцы) закрыта для всех карт через
kernel `0x26944` (см. "Оси карт") - при sweep'е достаётся из той же механики
обёртка+finisher, отдельно решать не нужно. Множитель оси RPM закрыт (`x*50`,
единица rpm/50 - см. "Множитель оси RPM = 50"). Опционально остаётся трейс
переменных нагрузки для их физических единиц.
